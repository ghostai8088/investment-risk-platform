## Key Learnings
- **THE derived-MAX cursor fail-open (NOTIF-1 4-finder HIGH, 3-finder converged):** a "process each item once" cursor over an append-only stream that derives its high-water from `MAX(source_sequence_no)` CANNOT represent a gap. Per-item atomicity closes the fail-open WITHIN an item, but if the worker `continue`s past a FAILED earlier item and a LATER item commits, the global MAX leapfrogs past the gap → the earlier item is orphaned forever (silent no-notify). **Fix: STOP the batch (`break`) on the first non-dedup failure (fail-CLOSED head-of-line)**; the failed item + tail retry next tick. Per-item atomicity ALONE is insufficient with a derived global cursor.
- **tick×HTTP deadlock discipline (API-2b P1, reused by NOTIF-1):** the FROZEN `record_event` takes a per-tenant audit-chain ADVISORY lock held to commit. A single-transaction tick that holds it across breach ROW locks while HTTP verbs acquire row→advisory = a reachable 40P01. Fix: commit phases 1-2, run later phases as PER-ITEM top-level transactions so lock acquisition order is uniformly row→advisory. **4-finder correction:** deadlock-freedom rests on row-lock-BEFORE-advisory ORDERING (the FK insert takes FOR KEY SHARE on the breach row — there IS a row lock), NOT on lock absence. A future reorder (emit before insert) would reintroduce the hazard.
- **The RLS GUC re-arm is load-bearing:** `set_tenant_context` is transaction-local and clears at COMMIT. Any long-lived worker session that commits mid-flow and reads after MUST use `persistent_tenant_context` (an `after_begin` re-arm listener) or the post-commit work reads ZERO rows under RLS — the OQ-a silent-fail-open pattern.
- **Reverse-lookup RLS pattern (`holders_of_permission`):** "who holds permission X in tenant T" — permission/role_permission are the global catalog; role/user_role/app_user are tenant-scoped. MUST replicate `has_permission`'s effective-dated `user_role` window (`valid_from <= now AND (valid_to IS NULL OR valid_to > now)`) AND `app_user.is_active`, or expired/deactivated grantees get paged.
- **Epoch-aware guards over append-only logs (API-2b A-F1):** a "requires a prior step" control that checks set-nonempty is EPOCH-BLIND — after a REJECT re-opens a fresh epoch, the rejected response still satisfies "a response exists" so ACCEPT could ratify it. Guard must require an item from the CURRENT epoch (seq > the governing epoch-opening row's seq).
- **Actor-id canonicalization (D1, inherited API-2→API-2b):** the person-level SoD compares raw strings while the permission gate compares via PG's case-INsensitive uuid cast — canonicalize (`str(uuid.UUID(x))`) in the ACTOR DATACLASS `__post_init__` so stamp==compare for every caller. PG-specific defeat; SQLite CHAR GUID is case-sensitive → the case-variance proof is a UNIT test + a PG-tier HTTP replay.
- **Frozen-audit boundary:** never modify `audit/service.py`. Read the stream via the read-only `audit/queries.py` (added `list_events_since_sequence`, cursoring on the gap-free monotonic `sequence_no` not the string `event_time`); emit new audit codes caller-side reusing existing `record_event` kwargs. `sequence_no` is gap-free/monotonic because the writer assigns `last+1` under the advisory lock.
