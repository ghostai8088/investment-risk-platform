## 1. Scope

**In:** a **phase 4** of the per-tenant operational tick that consumes the tenant's `BREACH.*` audit stream since a DERIVED high-water (`MAX(source_sequence_no)`, OQ-4=B), resolves in-tenant recipients, attempts delivery via a pluggable **sink**, and appends a durable IA `breach_notification` attempt row per (event, recipient); the failure-isolation shape (**per-EVENT atomic top-level transactions**, the P1 deadlock discipline — see the impl note below); a **read** (`list_breach_notifications`, gated `breach.view`) + a thin HTTP `GET /breaches/{id}/notifications`.

> **Implementation-corrected design (folded from the 4-finder review; see §8c):** the cursor is the DERIVED `MAX(source_sequence_no)` (OQ-4=B, no watermark table), and each alarm event is processed in its OWN **per-EVENT atomic** top-level transaction (all its recipients committed together — NOT a per-recipient own-txn advance, which OQ-4=B makes unimplementable: a per-recipient commit would advance the derived `MAX` past the event on its first recipient). The worker **STOPS the batch on the first non-dedup failure** (`break`, not `continue`) so a later event's commit can never leapfrog `MAX` past an earlier failed one (the 4-finder HIGH). Wherever the prose below still says "watermark" / "per-attempt / per-recipient own-txn," read it as this per-event-atomic + derived-`MAX` + break-on-failure shape.

**Out:** a real egress channel with credentials (v1 ships a `LoggingNotificationSink`; SMTP/webhook is a later config-driven adapter — BR-10 forbids secrets in source anyway); automatic retry of a FAILED send (v1 records it terminal; retry policy is a named v2); a per-tenant/per-limit notification-target **config entity** (v1 resolves recipients from the entitlement tables; the config entity is a named v2); notifying on lifecycle transitions (assign/respond/review/close — workflow, visible in the UI, not alarms); the cadence that turns the tick (slice 3); the operations-UI notification view (slice 4 renders this slice's read). The `create_schedule` P3-5 guard + the OQ-a worker `--tenant` canonicalization remain **slice-3** carries.

## 2. The architecture — a decoupled audit-stream consumer as tick phase 4

**Why a cursor-consumer, not inline-at-detection (the rejected alternative).** Emitting a notification *inside* phase 2 (at `BREACH.DETECT`) / phase 3 (at `BREACH.ESCALATE`) is simpler but wrong here: (a) it would run a sink send + an attempt-row write + (OQ-5) an audit emit INSIDE phase 2's single commit, re-introducing exactly the lock-hold-across-work the API-2b P1 fix removed; (b) a sink failure could disturb breach recording unless separately isolated; (c) it can only ever see events from the path it is wired into. The **audit-stream cursor** (finder C's recommendation, C-F12) is decoupled, restart-resilient (re-scans from the watermark), source-agnostic (catches any future emitter of `BREACH.*`), and — as its own phase after the phases-1–2 commit — deadlock-safe by construction.

**Phase 4 placement + the P1 discipline.** `run_operational_tick_for_tenant` (`scheduler.py:154-169`) becomes: phases 1–2 → commit → phase 3 (per-breach top-level txns) → **phase 4 (per-attempt top-level txns)**, all under the one `persistent_tenant_context` re-arm (`:157`, LOAD-BEARING — the RLS GUC is transaction-local; an un-re-armed phase-4 txn would read ZERO audit rows and notify NOTHING, the OQ-a fail-open pattern). Each notification attempt is its **own top-level transaction** (`begin`→work→`commit`). Verifier-confirmed: phase 4 takes **NO `breach`-row lock** — it does a lock-free `SELECT` over the audit stream, an `INSERT` into a fresh uncontended `breach_notification` row, and (OQ-5) a `record_event` advisory call; it shares no row with the HTTP breach verbs, so **tick×HTTP deadlock is genuinely impossible** (no row→advisory cycle can close). The one residual is the OQ-4-A watermark row (a mutable `UPDATE` = a row lock) which, if co-transacted with the advisory emit, admits a tick×tick cycle under overlap — resolved by advancing the watermark in its own advisory-free txn (§5); **OQ-4-B keeps phase 4 entirely row-lock-free** and the clean deadlock story holds with no caveat. The per-attempt-txn shape also bounds the blast radius of one failing send.

**The sink abstraction.** A `NotificationSink` Protocol (`deliver(notification) -> DeliveryResult`); v1 ships `LoggingNotificationSink` (a structured log line — the recorded attempt row is the system-of-record, not the log). A real EMAIL/WEBHOOK adapter is added later behind the same Protocol with NO schema change (its address resolution + credentials are config, added with provisioning — see §4). The sink NEVER reads cross-tenant and NEVER takes a DB lock.

## 4. Recipient resolution + the delivery address

**Recipients (v1, ratified rule — OQ-3=A):** the in-tenant holders of **`breach.review`** (the 2L oversight function — they own assign/escalate/close and are exactly who must know a breach appeared or blew its clock), resolved from the entitlement tables (`user_role`→`role_permission`→`permission`) within the acting tenant. The `recipient_reason` records the code. This is a pure in-tenant read (no cross-tenant, no BYPASSRLS), verifier-confirmed RLS-clean (`permission`/`role_permission` are the global catalog; `role`/`user_role`/`app_user` are tenant-scoped under FORCE RLS + explicit predicates). **No reverse-lookup helper exists** (`has_permission` is forward-only, `service.py:37-66`) — a new "holders of code X in tenant" query is required, and it MUST replicate `has_permission`'s effective-dated `user_role` window (`valid_from <= now AND (valid_to IS NULL OR valid_to > now)`, `service.py:59-62`) AND `app_user.is_active`, or an expired/deactivated grantee gets paged (verifier fold). A per-tenant/per-limit **notification-target config entity** (explicit recipient lists, tiered escalation chains, quiet hours) is the named **v2** — it is a provisioning surface, out of a bounded alarm slice.

**Delivery address (the honest v1 limitation):** `app_user` carries `display_name` + `external_subject` but **no contact/email column** (recon §5). So v1 records the *logical* recipient (`app_user.id`) + the attempt outcome; a real address needs an `app_user` contact field, which lands with **provisioning** (the same slice that owns the D2 one-human-one-row schema tightening). This is why v1 delivery is the `LoggingNotificationSink` + the durable evidence row: the governance question ("who was owed an alert, for what, when, with what outcome") is answered NOW and hash-anchored (OQ-5); the wire delivery is a credential-bearing adapter added with the contact schema. Stated so slice 4 / a demo does not expect a real email.

## 5. Idempotency, the watermark, and failure semantics (the load-bearing part)

**The watermark (OQ-4).** A per-tenant durable `sequence_no` high-water mark records "notifications processed through". Phase 4 each tick: read `BREACH.*` alarm events with `sequence_no > watermark` for the tenant (a NEW read `list_breach_events_since(acting_tenant, after_sequence_no, event_types)` in `audit/queries.py` — read-only, never imports the FROZEN writer; cursors on **`sequence_no`** — verifier-confirmed gap-free + strictly monotonic per tenant, assigned `last+1` under the per-chain advisory lock — because `event_time` (the only existing filter) is a string window with tie/precision risk). For each event in order: resolve recipients; per recipient, in its own top-level txn, append a `breach_notification` row (SAVEPOINT-guarded `IntegrityError` = already done, benign) and attempt the sink; then (subject to the all-recipients-durable rule above) advance the watermark. The **per-(event, recipient) unique key is the true idempotency backstop**; the watermark is the scan optimization. The verifier sharpened the A/B tradeoff:

- **OQ-4-A — an explicit mutable per-tenant `notification_watermark` EV row.** Clean "processed-through" semantics; a zero-recipient event advances it with no row written (no wart). COST: a second table (EV, not IA) AND a mutable row lock — its `UPDATE` must run in its own advisory-free txn (never co-txn with a `record_event` advisory call) or two overlapping same-tenant ticks can cycle (watermark-row↔advisory). HTTP never touches it, so the risk is tick×tick only and only under overlap (infra guarantees one tick per tenant, but that is not DB-enforced).
- **OQ-4-B — derive the high-water from `MAX(source_sequence_no)` on `breach_notification`.** NO extra table and **phase 4 then takes NO row lock at all** — the clean "row→advisory uniform, tick×tick impossible" story holds without caveat (the verifier's point). COST: a no-recipient event must write a terminal `SUPPRESSED` row to advance the derived MAX, and that sentinel's `recipient_id` MUST be a **fixed non-null sentinel** (e.g. the all-zeros UUID) — a NULL would defeat the `(tenant, seq, recipient)` unique key under Postgres NULL-distinct semantics and admit unbounded duplicate sentinels on crash-retry (verifier fold 2).

**Failure isolation (the fail-open lesson) — REVISED per the verifier's BLOCKING fold.** Two distinct outcomes: (i) a *sink send* failure records `outcome=FAILED` + `failure_reason` and **commits** the row (durable evidence) — a normal terminal outcome, never swallowed as "notified"; (ii) an *unexpected exception* while building/inserting one recipient's row rolls back THAT attempt's txn with **no durable row**. The load-bearing rule (the fail-open the slice exists to close): **the watermark advances past an event E only after EVERY resolved recipient of E holds a durable `SENT`/`FAILED`/`SUPPRESSED` row.** If any recipient of E raised (case ii), the watermark does NOT advance past E — E is re-processed next tick, and the unique key dedups the recipients that already committed. Without this, a per-event advance + "the rest of the tick proceeds" would step the watermark past an errored recipient who has no evidence row and is **never revisited** — a silent no-notify, the exact fail-open this whole slice targets. The watermark advance is **monotonic** (`GREATEST(watermark, E.sequence_no)`) so an overlapping slower tick can never regress it, and (under OQ-4-A) is committed in its **own advisory-free top-level transaction** (never in the same txn as a `record_event` advisory-lock call — the verifier's tick×tick lock-order fold; OQ-4-B has no watermark row so no such txn exists). A tick death mid-phase-4 leaves the watermark at the last fully-processed event → next tick resumes there (**at-least-once EVIDENCE**); the unique key makes the re-attempt of an already-recorded (event, recipient) a benign dedup (**at-most-once per recipient**).

**The honest limitation (state it plainly at the gate):** v1 guarantees at-least-once *evidence* (the CRO-was-owed-an-alert row), NOT at-least-once *wire delivery*. A transient sink outage commits a `FAILED` row that occupies the unique key and is **never auto-retried** — that recipient is permanently un-notified on the wire until the v2 retry policy ships, carrying only the FAILED evidence. This is the deliberate v1/v2 line, surfaced so the ratifier is not surprised.

**Retry (v1 = none, by precedent).** A `FAILED` attempt is **terminal** in v1 — recorded as evidence, not auto-retried (the `ScheduledRun` FAILED-dispatch precedent: the bucket is occupied, the tick is consumed). A bounded-retry policy (max-N, backoff, a `GIVEN_UP` terminal) is a named **v2** — it requires the unique key to admit multiple attempts per (event, recipient) (e.g. `+attempt_no`), a design the v1 key deliberately defers.

## 8. Open questions for the ratification gate (Tier-3)

**OQ-NOTIF-1-1 — v1 delivery mechanism.** **A [rec]:** record-first — a durable `breach_notification` attempt row is the system-of-record + a `LoggingNotificationSink`; a real EMAIL/WEBHOOK channel is a later config-driven adapter behind the `NotificationSink` Protocol (no schema change; credentials arrive with provisioning; BR-10 forbids secrets now). **B:** wire a real channel (SMTP/webhook) in this slice. *Recommend A — matches the "governed evidence first, real integration after the build" standing note; a real channel needs an `app_user` contact field (provisioning) and secrets management this slice should not own.*

**OQ-NOTIF-1-2 — the notifiable event set.** **A [rec]:** the two **alarm** events `BREACH.DETECT` + `BREACH.ESCALATE` (a breach appeared; a deadline blew), carrying the source `severity` in the payload so a future sink can filter HARD/SOFT. **B:** only the `severity="warning"` subset (HARD-`DETECT` + all `ESCALATE`), so a SOFT (advisory) breach pages no one. **C:** the full `BREACH.*` lifecycle. *Recommend A — DETECT+ESCALATE are the alarms; lifecycle transitions are workflow (visible in the UI, slice 4); B is a viable "warnings-only" tightening but couples the alarm rule to the HARD/SOFT severity map — carrying severity in the payload lets the recipient/sink decide. Not C (assign/respond/review/close are not alarms). Note (verifier): under A a SOFT `BREACH.DETECT` carries `severity="info"` (`service.py:709`) yet still pages a recipient — a deliberate consequence of the event-type rule, not a defect (severity rides in the payload for the sink to filter); if you want SOFT breaches to page no one, that is exactly OQ-2-B.*

**OQ-NOTIF-1-3 — recipient resolution.** **A [rec]:** a ratified role-based rule — the in-tenant holders of `breach.review` (the 2L oversight function), `recipient_reason` recorded. **B:** a new per-tenant/per-limit `notification_target` config entity (explicit lists, escalation chains). *Recommend A — the recipients ARE the oversight function, resolvable from the entitlement tables with zero new provisioning surface; B is a named v2 (config + a management API + its own review).*

**OQ-NOTIF-1-4 — the cursor mechanism.** **A:** an explicit mutable per-tenant `notification_watermark` EV row ("processed through `sequence_no` N"; clean on no-recipient events) — but a second table + a mutable row lock that must advance in its own advisory-free txn to avoid a tick×tick cycle. **B [rec, post-verifier]:** derive the high-water from `MAX(source_sequence_no)` on `breach_notification` — zero extra tables, phase 4 stays **entirely row-lock-free** (the clean tick×tick-impossible story holds with no caveat), at the cost of a fixed **non-null** `SUPPRESSED` sentinel row per no-recipient event. *The draft recommended A for its clean semantics; the verifier's lock-order analysis tilts the recommendation to **B** — it removes the only residual deadlock surface and the second table, and the sentinel is a well-understood minor wart (all-zeros UUID), matching the platform's recompute-from-source aesthetic. A remains viable if you prefer an explicit, inspectable "processed-through" cursor over a derived MAX; then the own-txn advance rule (§5) is mandatory.*

**OQ-NOTIF-1-5 — a NOTIFY.* audit code (the only mint at issue).** **A [rec]:** mint a minimal NOTIFY.* family (e.g. `NOTIFY.DISPATCH`, or `NOTIFY.SENT`/`NOTIFY.FAILED`) via R-07 and emit ONE per attempt, so "the CRO was alerted" is **hash-chain-anchored** tamper-evident proof (the compliance point of the whole slice), not merely an append-only row. **B:** no mint — the `breach_notification` IA row (append-only + P0001 trigger + RLS) is sufficient evidence; keep the slice mint-free. *Recommend A — the alarm's compliance value is provable delivery; the audit ledger is where proof lives, and the emit is deadlock-safe under the per-attempt-txn shape. B is leaner and the IA row is strong, but the hash chain is the difference between "a row says we alerted" and "an ordered, tamper-evident ledger proves we alerted". This is a genuine Tier-3 governance call.*

## 8b. Pre-ratification verifier — the eight attacks, adjudicated (the ES-1 lesson)

An independent adversarial verifier ran against the draft + the live code before this gate. **Design fundamentally sound; 1 BLOCKING fold + 1 conditional-BLOCKING fold, all folded above.**

1. **Phase-4 lock order — CONFIRMED (tick×HTTP impossible) / COMPLICATED (OQ-4-A tick×tick).** Folded into §2/§5: phase 4 holds no breach-row lock; the OQ-4-A watermark advance is own-txn advisory-free; OQ-4-B is row-lock-free outright (and the recommendation moved to B).
2. **Watermark / at-least-once — COMPLICATED → the one BLOCKING fold.** The fail-open silent-skip (advancing past an errored recipient with no evidence row) is closed by the "advance only after every recipient of E holds a durable row; an exception blocks the advance" rule + monotonic `GREATEST` (§5).
3. **`BREACH.DETECT` breach_id — CONFIRMED.** DETECT's id = `entity_id`; ESCALATE's = `after_value["breach_id"]` (its `entity_id` is the `breach_action` id). The per-`event_type` extraction trap is now spelled out in §3.
4. **FROZEN audit boundary — CONFIRMED.** The since-sequence read lands in the read-only `audit/queries.py`; a NOTIFY.* emit reuses existing `record_event` kwargs. `audit/service.py` is untouched.
5. **Recipient resolution — CONFIRMED (RLS-clean).** The new reverse-lookup query must carry the effective-dated `user_role` window + `app_user.is_active` (§4). `app_user` has no contact column — the record-first v1 is justified.
6. **No-recipient cursor stall — COMPLICATED (conditional BLOCKING).** Under OQ-4-B the sentinel `recipient_id` MUST be non-null (a NULL defeats the unique key — Postgres NULL-distinct); folded into §5/OQ-4. OQ-4-A has no stall.
7. **Idempotency vs retry — CONFIRMED consistent + honestly disclosed.** The at-least-once-EVIDENCE (not delivery) distinction is now stated bluntly (§5): a FAILED row is permanent non-delivery until the v2 retry.
8. **Scope / counts — COMPLICATED (undercount).** The "ONE new IA entity" line is now conditional on OQ-4 (4-A adds a second, EV, `notification_watermark` table); counts 23/38/109 unaffected; `breach.view` reuse verified legitimate.

## 8c. 4-finder adversarial review — folds (1 HIGH, converged by 3 finders; all folded)

Four independent finders (fail-open/cursor; concurrency/deadlock; boundary/security; doctrine/honesty) re-probed the shipped code. **Hard invariants all intact** (FROZEN `audit/service.py` byte-untouched; no BYPASSRLS; no new permission; counts 23/38/109; RLS-clean recipient resolution + reads; the mint scoped to `NOTIFY.DISPATCH`). Folds:

- **HIGH — the derived-`MAX` cursor + `continue`-past-failure = a permanent silent no-notify (3 finders converged → CONFIRMED-blocking).** My per-event atomicity closes the fail-open WITHIN an event, but the worker loop processed events oldest-first and `continue`d past a failed EARLIER event; because `MAX(source_sequence_no)` is a GLOBAL max, a later event committing then advanced the cursor past the earlier gap → the earlier alarm orphaned forever. **Fixed:** `poll_tenant_notifications` now **`break`s on the first non-dedup failure** (fail-CLOSED head-of-line — the derived `MAX` can never leapfrog a gap; the failed event + tail retry next tick). A permanently-poison head event stalls the tenant's queue with loud logs — a v2 dead-letter/skip-after-N is the named refinement.
- **MED — the "phase 4 takes NO breach-row lock" rationale was factually wrong (finder 2).** Each `breach_notification` INSERT takes `FOR KEY SHARE` on its `breach` FK row. Deadlock-freedom actually rests on **row-lock-BEFORE-advisory ordering, uniform with the HTTP verbs** (`FOR UPDATE` then advisory) — not on lock absence. Corrected in the worker/service docstrings so a future reorder (emit before insert) is correctly seen as re-introducing the hazard.
- **MED — the sink ran under the advisory lock for recipients 2..N (finder 2).** `notify_for_event` now delivers to ALL recipients FIRST, then records + emits — so NO sink runs while the per-tenant audit advisory is held (harmless for v1 LOG, but the promised drop-in v2 network sink would otherwise hold the audit-chain lock across I/O, the API-2b P1 anti-pattern).
