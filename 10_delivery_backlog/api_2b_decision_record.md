## 2. The two blocking pre-fixes (audit headline — service-side, land BEFORE the router)

**P1 — the tick commit topology (B-F1 CRITICAL; gate OQ-3).** Recommended A: `run_operational_tick_for_tenant`'s phase 1–2 work commits FIRST; phase 3 (deadline escalation) becomes PER-BREACH TOP-LEVEL transactions — every transaction in the system then acquires breach-row → advisory in the SAME order, making the tick×HTTP (and the pre-existing tick×tick) deadlock structurally impossible. **Verifier-verified complete:** phases 1–2 take ZERO row locks (`scheduling/service.py` has no `FOR UPDATE`; phase-2 `evaluate_limit` only INSERTs; HTTP limit verbs hold limit-row→advisory but nothing ever holds advisory→wants-limit-row), so after P1 no transaction anywhere holds the advisory lock while waiting on a row lock. Semantically safe: phase 3 never depends on uncommitted phase-1/2 state (a breach detected this tick has no `response_due` — the OD-LIM-1-G note at `scheduler.py:132-135`); each escalation is independent, idempotent (`uq_breach_escalation` + all conditions re-checked under the lock), and crash-window-free (uncommitted escalations re-select next tick; committed ones dedup). **Re-ratifies OD-LIM-1-G's single-terminal-commit wording** (the SAVEPOINT-per-item isolation INSIDE each phase is unchanged). **⚠ THE VERIFIER'S BLOCKING FOLD — the GUC re-arm:** `set_tenant_context` is TRANSACTION-local and auto-clears at COMMIT (`tenant.py:34-43`) — a naive mid-tick commit would run phase 3 RLS-UNARMED → every breach invisible → **silent zero-escalation, the OQ-a fail-open pattern**. The implementation MUST use `persistent_tenant_context` (`tenant.py:62-95`, the MD-H1-incident re-arm listener — arms at every new transaction) around the whole tick, and the PG regression MUST prove a post-commit phase-3 transaction still sees the tenant's breaches. API side: a deadlock victim surfaces as a wrapped `OperationalError` — detect via the `.orig` sqlstate `40P01` and map to **503 + Retry-After** (static body, `db.rollback()` first, NO post-rollback DB reads — B-F8); never a raw 500. Proof: a two-session PG regression constructing the exact interleaving.

**P2 — the epoch-aware review guard (A-F1 HIGH; adopted A-OQ3=A uniform).** `review_breach` additionally requires a `1L_RESPONSE` with `seq > _governing_assign(...).seq` — a response FROM THE CURRENT EPOCH — for ACCEPT and REJECT alike; else `BreachTransitionError` (→409). Closes the reject→escalate→ACCEPT-the-rejected-response→close defeat with zero governance loss (verified against all shipped legitimate flows). Regression = the exact defeat sequence refused + the three legitimate flows green.

## 3. The ownership cluster (gate OQ-1 + blocking demands)

Per the audit: REJECT re-opens with `assigned_to=None` and no verb can ever re-assign — the queue's owner concept goes NULL on the first REJECT. **OQ-1=A [rec]:** `review REJECT` carries optional `assigned_to`, default = carry-forward of the prior epoch's assignee; no standalone reassign verb; NO owner-changing row outside the REJECT path may restart `response_due`. **Blocking regardless of OQ-1:** `assign_breach` (and REJECT-with-assignee) canonicalizes via `_canonical_actor_id` and resolves the assignee — EXISTS, ACTIVE, same-tenant `app_user` — INSIDE the service AFTER `_lock_breach` (P3-5 doctrine; the raw-SQL existence-check precedent), stamping the RESOLVED canonical id; empty/blank refused. The ROUTER additionally refuses an assignee not holding `breach.respond` (C-OQ2=B — `has_permission` at the API layer keeps entitlement imports out of the shared package; post-assign revocation strands → escalation is the designed backstop, stated). Pool-model respond RATIFIED (A-OQ4=A): any `breach.respond` holder may respond; `assigned_to` is the accountability pointer + queue key, not a gate.
