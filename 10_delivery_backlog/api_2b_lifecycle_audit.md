## The two headline findings

**B-F1 (CRITICAL) — advisory×row lock-order inversion: a tick×HTTP deadlock is reachable the moment the first breach verb ships.** Every audit write takes `pg_advisory_xact_lock(tenant_chain)` FIRST-thing in the FROZEN `record_event` (`audit/service.py:35-46,127`), and a PG advisory xact lock is held to top-level commit. The worker tick is ONE transaction across all three phases (`scheduler.py:142-150`; single commit `db/tenant.py:141-144`), so its first audit emit (phase 1 governed run, or phase 2 `BREACH.DETECT`) pins the advisory lock for the whole tick; phase 3 then takes breach row locks (`lifecycle.py:420→121-125`). An HTTP breach verb acquires in the OPPOSITE order: `_lock_breach` row lock → insert → `record_event` → advisory. Interleaving: tick holds `advisory(T)`, reaches breach B, waits on `row(B)`; the human's respond holds `row(B)`, waits on `advisory(T)` → cycle → PG 40P01 kills one. If the human is the victim it surfaces as an unmapped `OperationalError` → **500**. API-2/limits could NOT hit this (`evaluate_limit` never row-locks a limit) — API-2b is the first surface where HTTP and the tick lock the SAME rows. A tick×tick sibling of the same inversion pre-exists (VERIFIER-F3-MED1's id-ordering fixed row↔row order only, not row↔advisory). **Fix (recommended, needs OD-LIM-1-G re-ratification):** commit the tick's phases 1–2, then run phase 3 as PER-BREACH TOP-LEVEL transactions — order becomes row→advisory UNIFORMLY across tick and HTTP (deadlock-free by uniform ordering); escalations are independent and idempotent (`uq_breach_escalation` + every condition re-checked under the lock), so per-breach commits are semantically safe. Plus: a deliberate 40P01 mapping at the API (503 Retry-After — never a raw 500) and a two-session PG deadlock regression.

**A-F1 (HIGH, borderline CRITICAL) — the review guard is EPOCH-BLIND: ACCEPT can ratify an already-REJECTED response.** `review_breach` requires only that the all-time responder SET is non-empty (`lifecycle.py:343-347`); `_prior_1l_responders` has no seq/epoch predicate (159-169). Defeat (all planned HTTP verbs + one tick): assign(seq1) → respond(seq2) → review REJECT(seq3 → ASSIGNED, fresh due) → nobody responds → deadline passes → tick ESCALATEs(seq4) → review **ACCEPT from ESCALATED**(seq5 — the rejected seq2 response satisfies the guard) → close(seq6). Terminal CLOSED with the only-ever response being the one the 2L organization formally adjudicated inadequate, zero fresh 1L work. MG-2's F1-HIGH1 fold closed the zero-response sibling; this is the rejected-response sibling. **Fix (service-side, BEFORE the HTTP surface ships): the epoch-aware guard — a `1L_RESPONSE` with `seq >` the governing epoch-opening action's `seq` (the latest `to_state==ASSIGNED` row, exactly `_governing_assign`) is required.** Synthesizer-verified against every legitimate shipped flow (happy path 2>1 ✓; escalated-after-response 2>1 ✓; reject-recovery 4>3 ✓; the defeat 2<3 REFUSED ✓). Applied uniformly to ACCEPT and REJECT (one rule; the only behavior lost — re-REJECTing an already-rejected epoch — has no governance value).

## The ownership cluster (A-F2 + A-F5 + C-F5 + B-F11 → one gate decision + one blocking demand)

A 2L REJECT re-opens to ASSIGNED via a row whose `assigned_to` is **None** (`review_breach` never passes it, `lifecycle.py:356-368`), and `assign_breach` is legal ONLY from DETECTED (87-88) — so epoch ≥ 2 has NO owner, its clock is running, and an assigned-to-me queue shows it in NOBODY's queue; there is also no path to fix a wrong/departed epoch-1 assignee. The machine stays live only because `respond_breach` never checks the actor against `assigned_to` (ownership is decorative in the service — the ratified "SHOULD"). Compounding: `assign_breach` stamps `assigned_to` RAW — empty string, garbage, cross-tenant, non-canonical casing all stamp cleanly (267-291), and a non-canonical stamp silently never matches a canonical queue filter (the D1 stamp≠compare bug's third instance, on a column `BreachActor.__post_init__` does NOT cover). **Demands:** (1) gate OQ-1 decides re-assignment (recommended: REJECT carries optional `assigned_to`, default carry-forward of the prior epoch's assignee; NO standalone reassign verb — any owner-changing row outside the REJECT path must NOT be able to restart `response_due`, else serial self-reassign defers escalation forever); (2) BLOCKING: `assigned_to` canonicalized via `_canonical_actor_id` + resolved (EXISTS, ACTIVE, same-tenant `app_user`) INSIDE `assign_breach` (the P3-5 in-service guard doctrine; raw-SQL existence check per the `service.py:412-421` precedent; placement AFTER `_lock_breach` per B-F11), stamped as the RESOLVED canonical id; empty refused; (3) the router ADDITIONALLY refuses an assignee who does not hold `breach.respond` (`has_permission` at the API layer — entitlement stays out of the shared limit package; a post-assign role revocation still strands → escalation is the designed backstop, stated); (4) pool-model respond (any `breach.respond` holder) RATIFIED explicitly — enforcement-to-assignee would deadlock post-REJECT until (1) lands, and shrinks resilience.
